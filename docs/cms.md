# CMS setup and operations

The CMS feature on `feat/portfolio-cms-neon` adds an authenticated editor at `/admin` for the portfolio's existing projects, designs, and profile. It does not expand the owner's professional content. This document describes the setup path; hosted Neon and Blob resources have not been provisioned for this branch.

## Content source and records

The public site uses the checked-in snapshots unless `CMS_CONTENT_SOURCE=database` is set. This static default is transitional. In database mode, public pages read only `cms.published_content`. Database or validation failures are returned as errors; the site does not silently switch back to the snapshots.

`npm run cms:seed` imports the current project/design/profile snapshots as revision 1 and publishes them. It includes existing project walkthroughs from `src/content/engineering.ts`. The seed is additive: it skips an existing `(kind, slug)` record, so rerunning it does not overwrite edits. Existing legacy image URLs remain accepted only by exact allowlist; the seed does not copy those images to Blob.

Project details render on request in both source modes. Before rendering `/project/{slug}`, `src/proxy.ts` checks the checked-in slug set in static mode or performs a fresh, parameterized existence query using `portfolio_public` in database mode. That database-mode guard adds one existence query per project-detail navigation; known content is then read through the published-projection cache. Missing slugs rewrite to the dedicated request-time `/project-not-found` recovery page with HTTP 404, `noindex`, and `no-store`, so recovery content remains in the HTML with JavaScript disabled. Waiting for the request keeps Next.js from applying the generated static 404's long cache lifetime; the uncached negative response cannot hide a newly published slug after the fresh existence query succeeds. Direct requests to `/project-not-found` also receive HTTP 404, `noindex`, and `no-store`. If the database guard fails, the request returns 503 without falling back to checked-in content.

The editor saves each change as a new immutable revision. Every update submits the revision it started from, so a stale editor receives a conflict instead of overwriting newer work. Restoring history creates another draft revision. Only the public projection is visible to public pages; saving or previewing a draft does not publish it.

All values below are server-side. Keep them out of source control and do not rename them with a `NEXT_PUBLIC_` prefix. Use different database URLs and CMS environment values for development, preview, and production.

## Provision the database

Provision the target Neon PostgreSQL database and one private Vercel Blob store for CMS media. Use one database with four separate principals. The three runtime roles are created and granted narrow privileges by the SQL migrations. `portfolio_public` can read only published content and published-media rows; `portfolio_cms` can manage editorial data; `portfolio_auth` can access the Better Auth tables and read the owner-membership record. The direct migration principal is used only by offline commands. Do not give an application runtime role ownership, superuser, role-creation, or bypass-RLS privileges.

For hosted Neon, keep the direct connection URL for migrations and provide a matching pooled endpoint template to generate the three runtime URLs. The helper supports Neon poolers in AWS and Azure regions and checks provider, region, endpoint, port, and database. Omitting the template makes the helper reuse the migration host, which is suitable for local PostgreSQL but is not the intended hosted Neon runtime configuration. The runtime URLs need the matching role names and TLS; the application verifies remote TLS certificates. `cms:migrate` checks its migration principal and records file checksums. Add a new numbered SQL migration for schema changes; never edit a migration file after it has been applied.

1. Install the locked dependencies with `npm ci` and provide `DATABASE_URL_MIGRATIONS` to the setup process through a private environment or secret manager.
2. Run `npm run cms:migrate` against the direct endpoint. This creates the CMS/Auth schemas, runtime roles, least-privilege grants, and the migration ledger.
3. Run `npm run cms:credentials` with `DATABASE_URL_MIGRATIONS` available to the setup process. For hosted Neon, also provide `DATABASE_URL_RUNTIME_ENDPOINT` so runtime URLs use the pooler; use a direct Neon URL for migrations. The migration URL permits only one each of `sslmode`, `channel_binding`, and `options=endpoint=...`, with no other query parameters. For a local database, omit `sslmode` or set it to `disable`; remote URLs must use `require`, `verify-ca`, or `verify-full`. `channel_binding` may be `disable`, `prefer`, or `require`; local `require` is rejected. An `options` value must be a validated `endpoint=...` route. The optional runtime template must be credential-free and secure, use only the same unique query parameters, and identify the matching provider, region, endpoint, port, and database. If an endpoint option is present, preserve the migration URL's route. The command creates the output file exclusively before connecting, then checks the writable migration principal, PostgreSQL 16 or newer, TLS/database route, runtime-role attributes and memberships, and managed schema ownership before setting random runtime-role passwords. It writes exactly the three role-specific URLs to the ignored `.env.cms.runtime.local` with owner-only `0600` permissions. Generated remote URLs carry `sslmode=require`, plus validated `channel_binding` and endpoint-routing values when set. It never prints the generated URLs and stops before connecting if that file already exists. The generated file does not contain the migration URL, authentication secret, bootstrap credentials, or Blob token. Keep it private and do not commit or paste its contents into logs or messages.
4. For a local trusted shell, source `.env.cms.runtime.local` to provide the three generated URLs to command processes. For the Next.js app, either start it from that shell or copy only the three generated lines into ignored `.env.local`. Configure `CMS_CONTENT_SOURCE`, `CMS_ENVIRONMENT`, `BETTER_AUTH_URL`, `BETTER_AUTH_SECRET`, and `BLOB_PRIVATE_READ_WRITE_TOKEN` separately. The deployed app receives only its three pooled role URLs, never the direct migration URL.
5. Run `npm run cms:seed` with `DATABASE_URL_CMS` available to the process. Confirm the imported entries in `/admin` before switching the public environment to database mode.

The migration and credential commands need network access to the selected database. A local PostgreSQL instance can be used for development and tests. A successful local run does not establish hosted Neon or Blob configuration.

The credential command changes the three runtime role passwords in place. Plan a maintenance window and update runtime configuration together. It refuses to overwrite an existing `.env.cms.runtime.local` before connecting; handle that secret file deliberately as part of the rotation procedure.

## Bootstrap the owner and enroll MFA

Owner creation is an offline one-time operation, not a public registration route. Sign-up is disabled in the web application, OAuth providers are not configured, and the bootstrap command rejects credentials passed as command-line arguments.

Provide `CMS_BOOTSTRAP_EMAIL` and a 12–128 character `CMS_BOOTSTRAP_PASSWORD` only to the one-off `npm run cms:bootstrap-owner` process, along with `DATABASE_URL_AUTH`, `DATABASE_URL_MIGRATIONS`, `BETTER_AUTH_URL`, and `BETTER_AUTH_SECRET`. `CMS_BOOTSTRAP_NAME` is optional. The command refuses to run after an active owner has been bootstrapped. Remove the temporary bootstrap values from the process environment when it exits.

Open `/admin/login` at the configured origin, sign in with the owner credentials, and complete verified TOTP enrollment at `/admin/security`. Store the generated backup codes in the owner's password manager. Authenticator backup codes are encrypted in the auth database. The account is not allowed to edit until TOTP is enabled. Password login is rate limited; repeated failed TOTP attempts trigger a temporary lockout. The Better Auth configuration revokes sessions when a password reset occurs, but this branch does not configure a self-service password-reset email flow.

The Better Auth session lasts 12 hours and refreshes after one hour. Publishing and unpublishing require a session created by a fresh password and TOTP or backup-code verification within the previous 30 minutes. Ordinary draft saves and history restores still require an active verified-owner session.

## Edit, preview, and publish

Use `/admin` to open a project, design, or profile entry. Save creates a new draft revision. The private preview is visible to the verified owner, carries noindex metadata, and is not read from the public content cache. Its image endpoint uses `private, no-store` and bypasses Next Image Optimization. Publishing a saved revision requires recent MFA and commits the published content projection, associated published-media registry rows, audit event, and outbox event together. Unpublishing removes the public projection and records its audit/outbox event in the same transaction.

After commit, the application expires the public content cache and revalidates affected routes and the sitemap. If cache invalidation fails after the database commit, the publication remains committed and its outbox event stays pending. Use the dashboard's retry control after service recovery; do not publish again to repair a cache event.

Public cache identity includes a hash of database host, port, name, runtime role, and the validated endpoint-routing value from `options=endpoint=...` when present, plus deployment environment, CMS environment, and preview branch. The URL parser allows only one each of `sslmode`, `channel_binding`, and a validated `options` endpoint value; credentials and unrecognized URL parameters are excluded. This keeps different routed database endpoints, preview deployments, and production cache entries separate. Set `CMS_ENVIRONMENT=preview` on preview deployments and ensure the hosting platform supplies its preview branch reference.

## Private CMS media

Use one Vercel Blob store with `BLOB_PRIVATE_READ_WRITE_TOKEN`. There is no public Blob token or public Blob store. Uploads begin in private staging, then the server decodes and normalizes a PNG, JPEG, or WebP image. New images are limited to 5 MiB and 16 megapixels, must be a single frame, have orientation normalized, and have metadata stripped. The normalized bytes are hashed and stored immutably at `verified/{uuid}/{sha256}`.

Drafts reference the app route `/media/published/{uuid}/{sha256}`. The Blob object remains private. The public route first requires the matching row in `cms.published_media`, then streams the corresponding private Blob object. That SQL registry row and the content projection are committed in the publication transaction, so a failed publication does not make its new image reachable. The delivery route sets a one-year immutable public cache response only after those checks; unknown or unregistered media returns 404. Once a version has been published, its registry row is retained when its content is later unpublished. The URL stays deliverable, and a browser or CDN may continue serving cached copies; unpublishing content cannot recall image bytes already delivered. Use a new content hash for changed image bytes.

Private previews use the authenticated `/api/admin/media/{uuid}` route with `private, no-store` headers and bypass Next Image Optimization. Never turn a verified or staged Blob object into a direct public URL, and never add a public access token. Existing allowlisted remote portfolio images remain available as their original exact URLs.

## Maintenance and recovery

- Before schema changes, take the database backup required by the target environment. Apply migrations with `DATABASE_URL_MIGRATIONS`; runtime connections must not run schema DDL.
- Treat `entry_revisions`, `audit_events`, and pending `publish_outbox` rows as recovery evidence. Restore an earlier revision through the editor to create a new draft, then review and publish it deliberately.
- If a cache refresh is pending, use the dashboard retry control after the cache service recovers. The database transaction remains authoritative.
- Keep the private Blob token limited to the one CMS store. Rotate it through the hosting secret manager and update the application environment; do not create a parallel public store for convenience.
- If the owner account needs to be disabled, revoke its active row in `auth.admin_memberships` through the offline database administration path. Do not grant ownership through Better Auth sign-up or a public endpoint.
- Keep separate database instances or credentials, `CMS_ENVIRONMENT` values, and preview-branch references for development, preview, and production. Do not point a preview deployment at production editing credentials.

The feature remains on the review branch and is not a production release. Do not treat documentation or local PostgreSQL checks as hosted Neon/Blob validation; see [verification](verification.md) for the recorded checks and their limits.
