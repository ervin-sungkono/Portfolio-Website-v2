# Parallax opportunities and UX guardrails

**Status:** implemented with the owner's subsequent hero-crossfade adjustment, 18 October 2026. The original proposal below is retained as design rationale; this implementation summary supersedes its hero image-travel recommendation. Actual checks are recorded in [verification](verification.md).

## Implemented treatment

- The hero crossfades from WeTrack to the next featured project, ChatGPT Clone, using a clearly marked placeholder for its forthcoming image. The image, project name, caption, and destination link fade together. Copy and frame geometry remain still; there is no hero image translation or scale. The fade spans 20–80% of the existing sticky scene and reverses with native scrolling.
- Exactly one preview is interactive and exposed to assistive technology. Keyboard focus holds that project fully visible until focus leaves. Reduced motion, mobile/coarse pointers, short viewports, oversized hero content, and no JavaScript retain the first preview without a reserved scroll scene.
- Homepage selected screenshots use ±1.5rem for the lead and retain ±1rem for its two supports; inspecting the compact ChatGPT/Pokedex crops ruled out the stronger ±1.25rem prototype. One AudioWaves artwork preview uses ±1.5rem. Matching overscan covers their travel. Whole-link tilt is removed on these selected project cards, and the hero hover lift is replaced with a stationary outline emphasis.
- Shared archive/filter/related-card travel remains ±1rem. The full design grid, project detail screenshots, About avatar, readable copy, navigation, forms, and filters receive no new scroll transforms. The new hero image requires no crop review until it is supplied.

## Original proposal

## Recommendation

Concentrate stronger parallax in the homepage sticky hero and the three selected project images. Keep screenshot content readable, with link geometry, captions, and actions steady; move only an image plane inside its existing clipped frame. Treat one homepage design preview as an optional, more expressive art surface after checking its crop. Do not raise the shared `ParallaxImage` default, which currently reaches the project archive, filtered results, and related-project cards as well as featured work.

The intended hierarchy is one focal motion scene at the top, a quieter echo on a small set of selected images, and still reading, filtering, and contact surfaces. Native scrolling and the existing desktop-only sticky hero remain in control.

## Coverage and interaction rules

- For a symmetric image travel range of `+d` to `-d`, the moving plane needs at least `d` of overscan at both frame edges: for frame height `H`, use a plane approximately `H + 2d` high, positioned `d` above the frame. Verify both endpoints. The current `±1rem` range uses the existing `H + 2rem` plane.
- Overscan is also crop. As an illustration, on a `14rem`-tall card, `d = 1.5rem` makes the plane `17rem` tall, about 21% taller than the visible frame; `object-fit: cover` then crops whichever axis the source aspect ratio requires. This is a calculation, not a measurement of a particular card. Check technical screenshots for clipped navigation, table columns, dialogs, or edge controls before approving each travel value. Keep screenshot movement smaller than artwork movement.
- Keep the scroll value on the image plane. The current `PointerSurface` transforms a parent of the link, so it also moves the target geometry. For the stronger hero and selected-media treatment, disable that whole-link tilt first; any later retained tilt must be confined to a non-interactive inner image plane inside the stationary link/frame. Do not raise the current `4deg` tilt or add more scale at the same time as increasing travel. If the selected images look over-tilted at scroll endpoints, reduce tilt on those surfaces instead of adding more overscan or scale. Keep the existing `1.012` hover scale bounded.
- The hero's current `1.04` scale and `5px` whole-link hover lift should not compound with a stronger whole-card scroll transform. The preferred design keeps the outer visual and its `<a>` geometry still and moves only the inner screenshot plane; captions and focus styling then remain anchored. If that cannot be achieved without cropping key UI, prefer a small drift in the existing decorative frame/backplate over moving the complete interactive card.
- A focused link should retain a stationary visible focus indicator and stable bounding box. Because only its non-focusable image plane moves in this proposal, a focus freeze is not required for geometry. Check keyboard focus during scroll; if the moving image underneath a focused link is distracting, freeze its inner scroll value while focused. Never suppress the visible focus state.
- Preserve the existing eligibility and fallback rules: at least `64rem` wide, at least `48rem` tall, fine pointer and hover, and no reduced-motion preference; keep the hero's content-fit check. Phone/tablet, coarse pointer, short viewport, reduced motion, and no-JavaScript layouts remain ordinary flow with no reserved parallax travel. Do not add wheel interception, scroll snapping, or extra scroll distance outside the existing sticky hero.
- Keep motion as decorative enhancement with a user preference fallback. See [W3C guidance on animation from interactions](https://www.w3.org/WAI/WCAG22/Understanding/animation-from-interactions.html) and [web.dev's animation guide](https://web.dev/articles/animations-guide) for reduced-motion and transform guidance.

## Staged rollout

1. Prototype the hero image plane only. Keep the copy, caption, and target geometry fixed; start at `±1.5rem`, then try `±2rem` only if the key WeTrack UI remains visible at both limits. Keep the current sticky timing and eligibility gate.
2. If the hero passes the crop and focus checks, opt the homepage lead project image into the same restrained range. Add the two smaller selected cards only if their compact frames retain enough UI detail.
3. Consider one homepage artwork preview after a separate crop review. Leave the project archive, filtered results, detail screenshots, and full design gallery at their current/static treatment.

## Acceptance checks for a later implementation

- On a fine-pointer desktop at representative `1024px` and `1440px` widths and a viewport taller than `48rem`, inspect the hero and opt-in images at start, midpoint, and end; reverse scroll, then confirm the hero releases into normal page flow.
- Check both themes and inspect technical image edges at every travel limit. Confirm the image frame never exposes the page background and important screenshot controls remain visible. For artwork, confirm text and focal subjects are not clipped.
- Compare the bounding boxes of the hero link, captions, card labels, and focused links before and during motion. They should not translate or resize. Use Tab and Shift+Tab to verify visible focus and normal link activation; check pointer hover and scroll together so tilt, hover scale, and parallax stay bounded.
- At `320`, `390`, and `820px`, with coarse pointer, at a short desktop viewport below `48rem`, and with reduced motion enabled, confirm ordinary layout, no sticky pinning, and no parallax travel. Also check enlarged text/reflow and no-JavaScript content visibility.
- Confirm native scrolling remains unchanged, there is no horizontal overflow, and no page content is obscured. These are proposed checks; this document does not claim they have been performed or that the site has been shown to conform to an accessibility standard.
